# HanzilookupNet

**A C# rewrite of the [`hanzilookup-js`](https://www.npmjs.com/package/hanzilookup-js) 1.0.3 npm package (offline handwritten Chinese character recognition), plus an Avalonia 12 control library and a demo application that draws the sub-stroke "skeleton" of what it recognizes.**

The JavaScript package is itself a modern rewrite of Gabor L Ugray's [HanziLookupJS](https://github.com/gugray/HanziLookupJS),
which derives from Jordan Kiang's original HanziLookup, and it matches against the `mmah.json` character data
derived from [Make Me a Hanzi](https://github.com/skishore/makemeahanzi).

| Project | Target | What it is |
| --- | --- | --- |
| `src/HanziLookup` | `net8.0`, `net10.0` | The recognizer: stroke analysis, sub-stroke matching, character data, sessions. No dependencies. |
| `src/HanziLookup.Avalonia` | `net8.0`, `net10.0` | Avalonia 12 controls: `StrokeInputCanvas` (capture + replay + analysis overlay) and `HanziStrokePreview` (sub-stroke skeleton). |
| `src/HanziLookup.Demo` | `net10.0` (switchable to `net8.0`) | Desktop demo application. |
| `tests/HanziLookup.Tests` | `net10.0` | xunit tests, including reference vectors generated by the original JavaScript implementation. |
| `tests/HanziLookup.Demo.Tests` | `net10.0` | Smoke test that runs the demo window on the headless Avalonia platform. |

## Quick start

```bash
git clone https://github.com/ilwren/HanzilookupNet
cd HanzilookupNet

# run the tests (this is what CI does); the second project drives the demo UI headlessly
dotnet test tests/HanziLookup.Tests/HanziLookup.Tests.csproj
dotnet test tests/HanziLookup.Demo.Tests/HanziLookup.Demo.Tests.csproj

# run the demo
dotnet run --project src/HanziLookup.Demo
```

The demo looks for the character data in `data/mmah.json` and `data/alnum.json` (repository layout) or next
to the executable; see [`data/README.md`](data/README.md) if a file is missing.

### Library usage

```csharp
using HanziLookup;

var data = HanziData.Load("data/mmah.json");          // 9507 characters, 156k sub-strokes
var matcher = new Matcher(data);                      // looseness defaults to 0.15

var strokes = new List<IReadOnlyList<StrokePoint>>
{
    new[] { new StrokePoint(32, 128), new StrokePoint(224, 128) }   // one horizontal line
};

var analyzed = new AnalyzedCharacter(strokes);
foreach (var match in matcher.Match(analyzed, limit: 8))
{
    Console.WriteLine($"{match.Character}  {match.Score:0.000}");
}

// ... or asynchronously, and without the JavaScript compatibility padding:
var clean = await matcher.MatchAsync(analyzed, 8, MatchOptions.Strict);
```

`HandwritingSession` keeps the interactive state for you (strokes, analysis, results, counters, async
recognition) and raises `Changed` / `RecognitionCompleted`:

```csharp
var session = new HandwritingSession(data);
session.RecognitionCompleted += (_, e) => Console.WriteLine(e.Results[0].Character);
session.AddStroke(new RawStroke(new[] { new StrokePoint(32, 128), new StrokePoint(224, 128) }));
```

### Drawing the strokes / showing what the matcher sees

Every sub-stroke is a quantized straight segment (direction, length, centre). `StrokeSkeleton` expands
those descriptors back into segments, so a character can be drawn **without** the original strokes and
**without** a CJK font:

```csharp
var entry = data.Find("學")!.Value;
var segments = StrokeSkeleton.FromRepositoryCharacter(data, entry);   // normalized 0..1 coordinates
```

The Avalonia package uses exactly that for its two controls:

```xml
<Window xmlns:hl="using:HanziLookup.Avalonia">
    <StackPanel Orientation="Horizontal">
        <hl:StrokeInputCanvas x:Name="Canvas" Width="420" Height="420" />
        <hl:HanziStrokePreview x:Name="Preview" Width="180" Height="180" Data="{Binding Data}" />
    </StackPanel>
</Window>
```

```csharp
Canvas.Session = session;        // captured strokes flow into the recognizer
Canvas.StartPlayback();          // re-draws the captured strokes point by point ("simulated writing")
Preview.ShowCharacter(data, "學");// or: Preview.ShowAnalysis(session.Analysis);
```

## What the demo shows

* handwriting capture with mouse, pen or touch on a 米字格 canvas (the captured points are mapped into the
  256 × 256 coordinate space the character data uses),
* **stroke analysis overlay**: the bounding box, the reconstructed sub-stroke skeleton (red) and the
  detected pivot points (blue) of the input,
* **recognition results** with scores, the number of compared candidates and the time taken,
* **candidate skeleton preview**: the sub-strokes stored in the data file expanded back into segments -
  this is the "simulated display of the strokes" part: no font or original stroke data involved,
* **replay**: the captured strokes are re-drawn point by point as an animation,
* loose (0 … 1) and candidate-count controls, and a switch that removes the candidates the original
  implementation returns without ever comparing them (see below).

![Sub-stroke skeletons reconstructed from data/mmah.json](docs/skeleton-reconstruction.png)

*Reconstructed sub-strokes - exactly what the preview panels of the demo draw. Generated with
`tools/preview/render-skeletons.py`.*

## Native AOT and trimming

Both libraries are written to be safe under `PublishTrimmed` / `PublishAot`: no reflection, no
`Activator`, no runtime code generation, no `dynamic`, and only the reflection-free corner of
`System.Text.Json` (`JsonDocument` + `Utf8JsonReader`). Both projects set `IsAotCompatible`, which turns the
.NET trim/AOT analyzers on for them and marks the assemblies as trimmable.

That is not taken on faith - CI verifies it on every push, in the `native AOT` job:

| What | How | Result |
| --- | --- | --- |
| `tools/aot-smoke` — the recognizer, end to end | `dotnet publish -r linux-x64` (AOT), then **run** it | 1.7 MB native binary, all reference-vector anchors assert |
| `src/HanziLookup.Demo` — the whole Avalonia app | `dotnet publish -r linux-x64 -p:PublishAot=true`, then run it headlessly under `xvfb-run` | 21 MB native binary; the window is built from compiled XAML, the data file loads, a stroke is drawn through the input canvas, candidates are matched and rendered, and the exit code reports the outcome |

The smoke test drives the same code paths the library exposes: `HanziData.Load` (9507 characters,
469479 packed bytes), `CompactDataDecoder`, `AnalyzedCharacter.FromStrokes`, `Matcher.Match` (score
`1.0199310536683939` for the single horizontal stroke) plus `MatchOptions.Strict`, `StrokeSkeleton`,
`HanziDataStore` and `HandwritingSession.RecognizeAsync`.

Publishing your own app as native AOT:

```bash
dotnet publish src/HanziLookup.Demo -c Release -r linux-x64 -p:PublishAot=true
```

Two things to keep in mind, both about the *application*, not these libraries:

* XAML stays compiled. `InitializeComponent()` -> `AvaloniaXamlLoader.Load(this)` is rewritten by the
  Avalonia build task into a direct populate call; loading XAML *at runtime*
  (`AvaloniaXamlLoader.Load(uri)`, `Avalonia.Markup.Xaml.Loader`) is reflection based and is not
  AOT-compatible - that is why it is marked `[RequiresUnreferencedCode]`.
* Prefer compiled bindings (`x:CompileBindings="True"` / `{CompiledBinding}`) over `{Binding}`, and
  avoid reflection-driven features such as `DataTemplate` type lookup by name. The demo does not rely on
  either: it wires its UI in code-behind, so it AOT-publishes as is.

## Recognizing what people actually draw

The ported algorithm is unchanged, but on its own it recognizes *data*, not handwriting. `mmah.json`
stores median strokes - clean polylines with evenly spaced points - while a pointing device reports
fast, unevenly sampled, shaky, slightly rotated and slightly mis-scaled input. The analyzer cuts a
stroke into sub-strokes by comparing the path length through three consecutive samples with the straight
distance between the outer two, so uneven sampling invents pivots that are not in the character: a
straight stroke analyses as 137 sub-strokes where the data has one, and it matches 丿 or 乙 instead of 一.

`StrokePreprocessor` is the input stage that closes that gap - drop duplicate points, average away the
tremor, keep the corners (Ramer-Douglas-Peucker), and re-space the rest evenly **without dropping the
corners on the way**. `HandwritingSession` applies it, and keeps the strokes exactly as they were drawn:

```csharp
var session = new HandwritingSession(HanziData.Load("data/mmah.json"));

// opt out, or retune for your own device - it is a plain record with init-only properties
session.Preprocessing = StrokePreprocessingOptions.None;
session.Preprocessing = StrokePreprocessingOptions.Default with { SimplifyEpsilon = 8.0 };
```

| | top-1 | top-5 |
| --- | --- | --- |
| Chinese characters written with variable speed, tremor, rotation and scale error, **without** the pipeline | 0% | 0% |
| the same, with `StrokePreprocessingOptions.Default` | see [`tools/data/evaluate.py`](tools/data/evaluate.py) | |
| the 72 digits / letters / punctuation of `data/alnum.json`, 3 samples each | 95.4% | 100% |

The numbers are measured, not estimated: `tools/data/evaluate.py` and `tools/data/check_alnum.py` write
characters the way a hand would and report what comes back, and the latter runs in CI on every push.

### Digits, Latin letters and punctuation

`data/alnum.json` is a second repository in the same format - 72 characters: `0-9`, `A-Z`, `a-z` and
`. , ! ? - + = / ( )`, generated by `tools/data/build_alnum.py` from the templates in
`tools/data/alnum_templates.py`. Load it on its own, or merge it with the Chinese set - the matcher has
no notion of script, so this is just a table concatenation with re-based offsets:

```csharp
var chinese = HanziData.Load("data/mmah.json");
var alnum = HanziData.Load("data/alnum.json");

var matcher = new Matcher(alnum);                              // digits and letters only
var both = new Matcher(HanziData.Concat(chinese, alnum));      // 9579 characters, one candidate list
```

The demo does exactly that: a selector switches between 汉字, 数字·字母·标点 and 全部. Expect `-` and `丨`
to compete with `一` and `I` in the merged repository - they *are* the same line - and expect the case of
a letter to be undecidable: the matcher normalizes each character by its own bounding box, so `c`/`C` and
`s`/`S` are the same geometry. The demo's case selector picks the reading you meant.

## Fidelity to the JavaScript original

The port is a line-by-line translation and is validated against the original implementation:

* `tools/reference/generate-reference-vectors.mjs` runs `hanzilookup-js@1.0.3` and writes
  `tests/HanziLookup.Tests/TestData/reference-vectors.json` (33 recognition cases - synthetic strokes,
  real median strokes of 一 人 大 中 水 明 你 好 學 書, looseness sweeps - plus the three score tables and
  samples of the cubic curve solver).
* The tests compare the integer parts of the analysis (pivot indexes, sub-stroke direction/length/centre,
  bounding rectangle) **exactly**, and the floating point parts within a 1e-9 relative tolerance, plus the
  diagnostic counters (`chars`, `subStrokes`) of every case.
* `tests/HanziLookup.Demo.Tests` additionally drives the demo window itself on the headless Avalonia
  platform: a stroke is drawn with simulated pointer input, matched, rendered and cleared again.
* CI runs the whole thing on GitHub Actions - two .NET SDKs, both packages, both test projects, the NuGet
  pack step - see [`.github/workflows/ci.yml`](.github/workflows/ci.yml).

Behaviours of the original that are intentionally reproduced (and documented in
[`docs/PORT-NOTES.md`](docs/PORT-NOTES.md)) include the *inert sub-stroke pre-filter*: `hanzilookup-js`
tests `repoChar[2].length` though `repoChar[2]` is a number, so candidates that were never compared come
back with a score of `-Infinity` whenever fewer characters pass the filter than the requested limit.
`MatchOptions.JavaScriptCompatible` (the default) reproduces that; `MatchOptions.Strict` removes exactly
those entries. Three deviations are deliberate: strokes without extent (a tap, or all points identical)
are skipped instead of producing `NaN`, the score matrix grows for inputs with more than 64 sub-strokes
instead of failing, and the base64 decoder copes with unpadded input.

## 中文说明

本仓库用 **C#（net8.0 / net10.0）+ Avalonia 12** 重写了 npm 包 **`hanzilookup-js` 1.0.3**（离线手写汉字识别），
并提供类库、Avalonia 控件库与演示程序：

* `src/HanziLookup` —— 识别核心：笔画分解（转折点 → 子笔画量化方向/长度/中心）、子笔画匹配、字符数据加载、交互会话。
  与 JavaScript 原版逐行对应，整数部分完全一致，浮点得分误差 < 1e-9（由自动生成的参考向量在 CI 中校验）。
* `src/HanziLookup.Avalonia` —— Avalonia 控件：`StrokeInputCanvas`（书写捕获、笔画重放动画、分析叠加层）、
  `HanziStrokePreview`（把量化子笔画还原成线段来“模拟显示笔画”，不依赖字体或原始笔迹）。
* `src/HanziLookup.Demo` —— 演示程序：手写输入、实时骨架/转折点/包围盒、候选列表与候选字骨架预览、宽松度与候选数调节。
* `tests/HanziLookup.Demo.Tests` —— 在 headless Avalonia 上启动真实窗口的冒烟测试（模拟指针书写、识别、渲染、清除）。

**手写预处理**：算法本身与原版逐行一致，但原版假设的是“数据”（`mmah.json` 里均匀采样的中位笔画），
而鼠标 / 手指 / 触控笔给出来的是速度不均、带抖动、轻微旋转与缩放的轨迹。`AnalyzedCharacter` 用“三个连续
采样点的路径长度 vs 首尾直线距离”来判断转折，采样不均就会凭空造出转折点：一笔直线会被切成 137 个子笔画
（数据里只有 1 个），候选在打分前就被过滤掉，结果匹配成 丿、丶、乙。`StrokePreprocessor` 就是补上这一段：
去重 → 滑动平均去抖 → RDP 保留拐角 → **等距重采样且保留所有拐角**（如果按固定网格重采样会把 `L` 的拐角抹平，
字母就识别不出来）。`HandwritingSession` 在“生成分析”时才做这一步，因此 `Strokes` 里存的仍是原始轨迹，
可直接用于回放；`session.Preprocessing` 可整体关闭（`StrokePreprocessingOptions.None`）或按设备重新标定。

**数字与字母**：`data/alnum.json` 是同格式的第二份字库（72 个字符：`0-9`、`A-Z`、`a-z` 以及
`. , ! ? - + = / ( )`），由 `tools/data/build_alnum.py` 从 `alnum_templates.py` 生成，
`tools/data/check_alnum.py` 做闭环校验（模拟手写后必须能识别回来，216 次采样 top-1 95.4% / top-5 100%），
CI 每次推送都会跑。识别器本身不区分文种，两份字库直接拼表即可：

```csharp
var both = new Matcher(HanziData.Concat(HanziData.Load("data/mmah.json"), HanziData.Load("data/alnum.json")));
```

演示程序里用下拉框在 汉字 / 数字·字母·标点 / 全部 之间切换。合并字库里 `-`、`丨` 会和 `一`、`I` 争候选
（它们本来就是同一根线）；字母大小写则无法区分——匹配器按各自包围盒归一化，`c`/`C`、`s`/`S` 几何完全相同，
所以演示程序提供了一个大小写选择框。

**原生 AOT**：两个类库都不使用反射 / 运行时代码生成（JSON 只用无反射的 `JsonDocument`），并开启了
`IsAotCompatible`（自动跑裁剪与 AOT 分析器、标记为可裁剪）。CI 每次推送都会实测：把 `tools/aot-smoke`
以 `PublishAot` 发布成原生程序并运行（1.7 MB，校验参考向量锚点），再把整个演示程序编译成原生二进制，
在 `xvfb-run` 下用 `--self-check-ui` 跑真实窗口（21 MB，编译期 XAML → 加载数据 → 通过输入画布写字 → 出候选）。
自己发布：`dotnet publish src/HanziLookup.Demo -c Release -r linux-x64 -p:PublishAot=true`
（注意：XAML 必须走编译期加载，运行时 `AvaloniaXamlLoader.Load(uri)` 与反射式 `{Binding}` 不属于 AOT 兼容范围）。

运行方式：

```bash
dotnet test tests/HanziLookup.Tests/HanziLookup.Tests.csproj        # 单元测试（含 JS 参考向量）
dotnet test tests/HanziLookup.Demo.Tests/HanziLookup.Demo.Tests.csproj  # 演示程序的 headless UI 冒烟测试
dotnet run  --project src/HanziLookup.Demo                          # 演示程序
```
